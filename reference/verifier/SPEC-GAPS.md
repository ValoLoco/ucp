# Chapter 01 spec gaps found while implementing

Status: every item below is an **open question**. The reference verifier makes a labeled reference choice for each so it can run, but none of these choices is normative and none changes the spec. Section references are to [specs/01-entity-record.md](../../specs/01-entity-record.md) unless noted.

| Id | Section | Gap | Reference choice (proposal) |
| --- | --- | --- | --- |
| G-01 | Serialization and digests; `signatures` row | Canonical serialization is unset (Q-005), so the signing payload bytes are undefined. | RFC 8785 JCS, integers only. |
| G-02 | `previousRecordDigest` row | Digest algorithm, encoding and digest input are undefined ("the digest algorithm named in the active signing profile", but no profile exists). Unclear whether the digest covers `signatures` and `anchorReceipt`. | `sha256:` + hex over JCS of the record without `anchorReceipt`, signatures included. |
| G-03 | Step 2; `authorityPolicy` row | Genesis has no predecessor, so step 2 does not say which policy authorizes a genesis record. | Genesis is checked against its own `authorizedKeys` and `authorityPolicy` (self-asserted). |
| G-04 | Step 2 | "unless the current record explicitly replaces policy per local rules" leaves policy replacement entirely to local rules. | No replacement; successors are always checked against the predecessor's policy and keys. |
| G-05 | Step 3 | Which record's `authorizedKeys` to use (current or predecessor) is not stated. Also undefined: whether a signature by a key outside `authorizedSigners` or unknown entirely is ignored or fails. | Predecessor's keys for successors. Valid signatures by keys outside `authorizedSigners` are ignored; unknown keyIds are ignored with warning `x-ref-unknown-signer`; any cryptographically bad signature makes the record invalid. |
| G-06 | Step 3; `authorizedKeys` row | "relevant validity window" has no reference time. `effectiveAt` must not be trusted (chapter 01, 00-conventions), yet no other signing time exists. | `validFrom`/`validUntil` compared against `effectiveAt`, flagged here as unsafe. |
| G-07 | Step 3; `revocationRef` | Revocation material format, freshness rule and the "definitive" test (invalid vs indeterminate) are undefined. Chapter 03 adds `maxRevocationDataAge` without a format. | `evidence.revocations[ref] = {"revokedKeyIds": [...]}`; missing material is indeterminate `revocation-data-missing`; staleness not evaluated. |
| G-08 | Steps 2 and 4 | How a verifier "obtains" the predecessor is undefined. If found by digest, step 4's `digest-mismatch` can never fire; it only fires when the predecessor is supplied positionally (as in the chapter 03 tip chain). | Both: positional `predecessor` input, else lookup by digest in the carried bundle. |
| G-09 | Step 5; chapter 03 Phase A | Chapter 01 step 5 says return indeterminate when registrar confirmation is unavailable; chapter 03 calls the same condition non-blocking. No offline registrar evidence format exists. | Policy flag: warning by default, blocking indeterminate when `registrarConfirmationBlocking` is true. Confirmation is never available offline in this reference. |
| G-10 | `anchorReceipt` row; step 6 | No anchoring profile is defined: no field naming the profile, no field for the committed digest, no proof encoding, no header data format (chapter 01 open question 3). | Requires `profile` string; optional `recordDigest` is compared to the record digest; everything else is indeterminate `anchor-data-unavailable`. |
| G-11 | Step 6; chapter 03 Phase D | Confirmation depth default and provisional-anchor rules live only in chapter 03 policy; chapter 01 says "stated Bitcoin confirmation assumptions" without a default (Q-009). | Not implemented; no anchored record can reach valid. |
| G-12 | Document object model; `anchorReceipt` row | Table says every record MUST contain all listed fields, but `anchorReceipt` "MAY be present" and `legalRegistrations`/`documents` are SHOULD-level content. Unclear which keys may be omitted. | All fields required except `anchorReceipt`; empty arrays allowed for `legalRegistrations` and `documents`. |
| G-13 | `authorizedKeys` row | "`publicKeyMultibase` or `publicKeyJwk` (one REQUIRED)" does not say whether both may appear, nor which key types and multicodec are allowed. | Exactly one; Ed25519 only (multikey 0xed01 or OKP JWK). |
| G-14 | `signatures` row | `suite` names a "signing profile" but no suite registry or signature encoding exists. Unsupported suite outcome (invalid vs indeterminate) is undefined. | One reference suite; any other suite gives indeterminate `x-ref-unsupported-suite`. |
| G-15 | Step 1 | Step 1 says "types violate this chapter" but chapter 03's code list has only `missing-field`; no code for a present but malformed field. | `x-ref-field-invalid`; `x-ref-not-canonicalizable` for values the encoding cannot carry. |
| G-16 | `authorityPolicy` row | No rule for `requiredSignatureCount` larger than the number of `authorizedSigners`, or `authorizedSigners` ids missing from `authorizedKeys`. | Both treated as malformed (step 1 invalid). |
| G-17 | `entityId` row; step 4 | `entityId` MUST stay unchanged, but no step checks it against the predecessor and no reason code exists. | Step 4 invalid `x-ref-entity-id-mismatch`. |
| G-18 | Steps 1 to 7 | Each step says "return", which reads as early exit, while step 7 says "aggregate the strongest failure". Unclear whether later steps run after a failure. | Early exit at the first step that is invalid or blocking indeterminate; step 7 aggregates warnings. |
| G-19 | `delegationPolicy` | Shape undefined (object or array of delegations), and how delegated keys interact with `requiredSignatureCount` is unstated (chapter 01 open question 2). | Shape-checked only, not evaluated. |
| G-20 | `protocolVersion` row | No list of supported versions exists. | Only `0.1.0` (the version used in chapter 01 examples). |
| G-21 | Verification method item 1 | "official test vectors once published": no process names who publishes official vectors. | The vectors in `test-vectors/ch01/` are reference vectors, not official. |
